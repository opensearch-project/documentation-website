# OTel trace processor

The `otel_traces` processor completes trace-group-related fields in all incoming OpenSearch Data Prepper span records by state caching the root span information for each `traceId`. It also enriches traces from generative AI (GenAI) agents and large language model (LLM) applications. For more information, see [GenAI agent trace enrichment](#genai-agent-trace-enrichment).

The processor was previously named `otel_trace_raw`. You can still use the `otel_trace_raw` name, but support for it will be removed in Data Prepper 3.0.
{: .note}

## Usage

This processor adds the following fields to span events:

* `traceGroup`: Root span name
* `endTime`: End time of the entire trace in International Organization for Standardization (ISO) 8601 format
* `durationInNanos`: Duration of the entire trace in nanoseconds
* `statusCode`: Status code for the entire trace

## GenAI agent trace enrichment

The `otel_traces` processor enriches traces from GenAI agents and LLM applications so that agent runs can be found, listed, and measured from the spans themselves, for example, in the OpenSearch Dashboards **Agent Traces** page. Enrichment is turned on by default, is available in Data Prepper 2.15 and later, and does not change traces that contain no GenAI data.

Enrichment matches attributes by their OpenTelemetry (OTel) key names, for example, `gen_ai.operation.name`, so the source must emit spans in the OTel format. The [`otel_trace_source`]({{site.url}}{{site.baseurl}}/data-prepper/pipelines/configuration/sources/otel-trace-source/) source defaults to the `opensearch` format, so set its `output_format` to `otel`. The [`otlp`]({{site.url}}{{site.baseurl}}/data-prepper/pipelines/configuration/sources/otlp-source/) source uses the `otel` format by default. The `opensearch` format rewrites attribute keys (for example, `http.method` becomes `span.attributes.http@method`), and the enrichment then finds no GenAI data.
{: .important}

For each trace in a batch, the processor applies the following steps in order:

1. [Vendor attribute normalization](#vendor-attribute-normalization)
1. [Flattened sub-key stripping](#flattened-sub-key-stripping)
1. [Root span enrichment](#root-span-enrichment)
1. [Agent root marker](#agent-root-marker)

To turn off all of these steps, set `disable_genai_enrichment` to `true`. Span attributes are then left as they arrive, and the processor creates no coverage cache.

### Vendor attribute normalization

Instrumentation libraries name the same data differently. For example, input tokens are `llm.token_count.prompt` in OpenInference, `llm.usage.prompt_tokens` in OpenLLMetry, and `gen_ai.usage.input_tokens` in the [OTel GenAI semantic conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/). The processor copies vendor attributes to their `gen_ai.*` names so that queries, dashboards, and the rest of the enrichment only need the standard names. The normalization follows these rules:

* The mappings are listed in [`genai-attribute-mappings.yaml`](https://github.com/opensearch-project/data-prepper/blob/main/data-prepper-plugins/otel-trace-raw-processor/src/main/resources/genai-attribute-mappings.yaml) and grouped by source: `openinference`, `openllmetry` (Traceloop), and `claude_code`.
* The original attributes are kept. The `gen_ai.*` copy is added next to them.
* A `gen_ai.*` attribute that is already on the span is never overwritten.
* When several attributes on one span map to the same `gen_ai.*` name, the one listed first in the mappings file is used. For example, the OpenInference `session.id` attribute is used before Traceloop's `traceloop.association.properties.session_id`; both map to `gen_ai.conversation.id`.
* Operation kinds are mapped to `gen_ai.operation.name` values. For example, the OpenInference `LLM` kind becomes `chat`, `AGENT` and `CHAIN` become `invoke_agent`, and `TOOL` becomes `execute_tool`.
* Some mappings wrap a single value in a JSON array, for example, a finish reason in `gen_ai.response.finish_reasons`.

Starting in Data Prepper 2.17, Traceloop session IDs (`traceloop.association.properties.session_id`) are mapped to `gen_ai.conversation.id`, which groups traces into sessions.

### Flattened sub-key stripping

Some instrumentations emit the same field twice: as a JSON string (for example, `llm.input_messages`) and as flattened sub-keys (for example, `llm.input_messages.0.message.content`). OpenSearch rejects such documents with a mapping conflict. When the parent string is present, the processor removes the indexed sub-keys. When only the sub-keys are present, they are kept so that no data is lost.

### Root span enrichment

The processor can copy `gen_ai.system`, `gen_ai.provider.name`, `gen_ai.agent.name`, `gen_ai.request.model`, and the trace's token totals from child spans onto the trace's root span. Attributes that the root span already has are kept. Values are taken from the outermost GenAI spans first (by earliest start time), then from other GenAI spans, and then from the remaining children.

The `genai_root_propagation` option selects which root spans receive the copies, as described in the following table.

Value | Root spans that receive the copies
:--- | :---
`ai_root` (default) | Only a root span that is its trace's AI root: a GenAI span, or a span marked `derived.gen_ai.is_root: true` at the source.
`all_roots` | Every root span, including non-GenAI roots such as the HTTP span that an agent runs behind. This is the behavior before Data Prepper 2.17.
`none` | No root span.

With `ai_root`, a non-GenAI root span keeps only its own attributes. Copying agent data onto it made the HTTP span appear to call a model and use tokens, combined parallel agents into one agent name, and counted the trace's tokens again for any consumer that sums usage across spans. The [agent root marker](#agent-root-marker) span carries this data instead.

Marking does not depend on this option: with `none`, a marked agent span still receives its descendants' token totals.

In Data Prepper 2.17, the default changed from copying onto every root span to `ai_root`. If your queries or dashboards read agent data, such as `gen_ai.agent.name` or token totals, from non-GenAI root spans, set `genai_root_propagation` to `all_roots` to keep the previous behavior, or read the data from the marked agent span.
{: .important}

### Agent root marker

Agents often run behind a service: the trace's root span is an HTTP or RPC span, such as `POST /plan`, and the agent span is below it. Consumers that list traces by their root span then miss the agent or show the HTTP span instead. Starting in Data Prepper 2.17, the processor marks the span that represents each agent run with `derived.gen_ai.is_root: true`. The marker follows these rules:

* **Marked spans**: Each outermost GenAI span of a trace is marked. This is a span that has `gen_ai.operation.name` and no GenAI ancestor: either the root span itself, when it is a GenAI span, or the agent span below a non-GenAI root.
* **Parallel agents**: When several top-level agents run under one root span, each is marked as one agent run.
* **Agents that call agents**: In a chain such as `invoke_agent` > HTTP client > HTTP server > `invoke_agent`, only the calling agent is marked because the called agent has a GenAI ancestor.
* **Token totals**: A marked span that reports no token usage of its own receives the usage of its descendants, counted as described in [Token usage](#token-usage).
* **Markers set at the source**: An SDK or the user can set the marker on a span. If any span in a trace is marked `true` at the source, the processor marks no other span in that trace. A span set to `false` is never marked, so setting `false` on a trace's outermost GenAI spans opts the trace out.
* **Spans without their root span**: Spans that are flushed after `trace_flush_interval` without their root span are still marked because the marker only needs the spans below it.

To list a trace's agent runs, query its marked spans. For data indexed before the marker existed, fall back to root spans that are GenAI spans.

#### Late spans and the coverage cache

The spans of one trace can arrive in several batches. A span that arrives after its agent span was processed is enriched without its ancestors, so it would appear to be outermost and would be marked as a second agent run. To prevent this, the processor records, per trace, which span IDs are already covered by a GenAI span or a marker, and checks this record when a span's parent is not in the batch. The coverage cache works as follows:

* Entries are kept for twice the `trace_flush_interval` plus the `trace_group_cache_ttl` (375 seconds by default), so they outlive the flush of spans that arrive without their root span.
* The cache holds at most `genai_coverage_cache_max_size` span IDs across all traces. Only traces with GenAI data are stored. The `genAiCoverageSpanIdCount` metric reports how full the cache is, in span IDs.
* The cache covers about `genai_coverage_cache_max_size` / (2 x `trace_flush_interval` + `trace_group_cache_ttl`) GenAI spans per second, which is about 1,300 spans per second by default. Above that rate, traces are evicted early and a late span can be marked again, so increase `genai_coverage_cache_max_size` for higher GenAI span rates.
* The covered-span lookup, the marking, and the update run atomically for each trace, so pipeline workers that process spans of the same trace at the same time do not both mark a span.

The coverage cache has the following limitations:

* A span that arrives after its trace's entry has expired or was evicted can be marked.
* If a trace's child spans are flushed before a GenAI root span arrives, both the root span and the outermost child span can be marked. Consumers should prefer the marked span that has no parent.
* If a called service's spans are flushed after `trace_flush_interval` without the caller's spans, the called agent is also marked and is listed as a separate agent run.

### Token usage

When the processor sums `gen_ai.usage.input_tokens` and `gen_ai.usage.output_tokens`, either onto a root span or onto a marked agent span, it counts only spans that have no ancestor that also reports usage. Agent spans such as `invoke_agent` often report the total of their own LLM calls, so adding every span that reports usage would count those calls twice. Token counting follows these rules:

* An ancestor's reported usage is assumed to include its subtree. A sub-agent that runs its own LLM calls under a parent that reports only its own usage is not added.
* A span that reports either token count is treated as reporting usage and keeps its own values.
* Token counts sent as numeric strings are read as numbers. Other values are ignored.

### Example

The following pipeline receives OTLP traces in the OTel format and writes enriched spans to OpenSearch. The GenAI options are shown with their default values:

```yaml
otel-traces-pipeline:
  source:
    otel_trace_source:
      ssl: false
      output_format: otel
  processor:
    - otel_traces:
        disable_genai_enrichment: false
        genai_root_propagation: ai_root
        genai_coverage_cache_max_size: 500000
  sink:
    - opensearch:
        hosts: ["https://opensearch:9200"]
        index_type: trace-analytics-plain-raw
```

## Metrics

The following table describes common [Abstract processor](https://github.com/opensearch-project/data-prepper/blob/main/data-prepper-api/src/main/java/org/opensearch/dataprepper/model/processor/AbstractProcessor.java) metrics.

| Metric name | Type | Description |
| ------------- | ---- | -----------|
| `recordsIn` | Counter | Metric representing the ingress of records to a pipeline component. |
| `recordsOut` | Counter | Metric representing the egress of records from a pipeline component. |
| `timeElapsed` | Timer | Metric representing the time elapsed during execution of a pipeline component. |

The `otel_traces` processor includes the following custom metrics:

* `traceGroupCacheCount`: The number of trace groups in the trace group cache.
* `spanSetCount`: The number of span sets in the span set collection.
* `genAiCoverageCount`: The number of traces in the GenAI coverage cache.
* `genAiCoverageSpanIdCount`: The number of span IDs in the GenAI coverage cache, in the same unit as `genai_coverage_cache_max_size`. Available in Data Prepper 2.17 and later.
